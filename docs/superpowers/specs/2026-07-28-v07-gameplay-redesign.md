# 今日の市長 v0.7 ゲーム性刷新 設計書

作成日: 2026-07-28  
対象リポジトリ: `TI-06/today-mayor`  
対象バージョン: `0.7.0`

## 1. 目的

v0.6までの「1日3件の案件を順番に処理する」ゲームループを廃止し、プレイヤーが市長として方針、予算、調査、大型事業を主体的に決める週単位の都市経営ゲームへ再構成する。

v0.7では次の課題を解消する。

- 毎回同じ案件処理を繰り返す作業感
- 市の予算残高、収支、支出後残高が分からない問題
- 政策の結果が街の見た目へ十分反映されない問題
- 突発イベントが単発で終わり、予測や準備ができない問題
- 住民が好感度ゲージとしてしか機能していない問題
- タヌキ秘書「ポン吉」の外見と演出が弱い問題
- スマートフォンで情報量と操作導線が整理されていない問題

## 2. スコープ

### 2.1 実装対象

| 改善領域 | 実装内容 |
|---|---|
| コアループ | 1日3件処理を廃止し、週単位へ変更 |
| 自動処理 | 軽微案件をポン吉が方針に沿って自動処理 |
| 主体的行動 | 重点政策、大型プロジェクト、地区投資、調査 |
| 目標 | 週次目標、任期目標、選挙公約 |
| キャラクター | 固定住民の個別ストーリーと分岐 |
| 街 | 政策・建設・災害結果を街の見た目へ反映 |
| イベント | 予告、調査、対処、続報の4段階化 |
| 選択情報 | 確定費用は表示し、将来リスクは一部非表示 |
| 演出 | ニュース速報、市民反応、週次ダイジェスト |
| 財政 | 市予算、週次収支、翌週予測、市債、予備費 |
| 通貨 | 市予算と衣装用葉っぱコインを完全分離 |
| ポン吉 | 3頭身のアニメ調SVGと状態連動アニメーション |
| UI | スマートフォン最優先の固定資金バーと5タブ構成 |

### 2.2 実装対象外

- v0.6以前のセーブデータ移行
- 旧セーブのバックアップ、復元、互換性維持
- Live2D、3D、WebGLによるキャラクター表現
- 実際の広告プロバイダーまたは決済プロバイダー接続
- リアルタイム対戦、チャット、ユーザー間取引
- 管理画面からのイベント追加機能

## 3. 旧データの扱い

v0.7は新規ゲームとして開始する。旧データは考慮しない。

### 3.1 端末保存

- Local Storageキーを`today-mayor-v07`へ変更する。
- 旧キー`today-mayor-v02`は読み込まない。
- 旧キーの削除は行わないが、ゲームから参照しない。

### 3.2 D1クラウド保存

- クラウドから取得した状態の`version`が`0.7.0`でない場合、その状態を読み込まない。
- v0.7初回起動時は新規状態を生成する。
- ログイン済みユーザーがv0.7を保存した時点で、`saves.state_json`をv0.7状態で上書きする。
- 旧状態の変換処理、退避テーブル、履歴移行は実装しない。

## 4. プレイ時間とゲーム進行

### 4.1 1週間の想定プレイ時間

1週間あたり7〜10分を目標とする。

通常週の能動操作は3〜5回に抑える。すべての曜日で必ず操作を要求せず、確認のみのフェーズを含める。

### 4.2 週フェーズ

| フェーズ | 表示名 | 主な処理 | 操作目安 |
|---|---|---|---:|
| `planning` | 月曜・方針決定 | 重点方針、予算配分、任意の大型事業開始 | 1〜2回 |
| `policy` | 火曜・重要政策 | 重要案件または住民ストーリー | 1回 |
| `warning` | 水曜・兆候 | イベント予告と調査判断 | 0〜1回 |
| `project` | 木曜・市政実行 | 大型事業、地区投資、住民ストーリー | 1回 |
| `response` | 金曜・議会／緊急対応 | 議会採決、事件対処 | 0〜1回 |
| `city_result` | 土曜・街の反応 | 見た目の変化、市民反応、続報 | 確認中心 |
| `settlement` | 日曜・週次決算 | 収支、目標、ニュース、次週予告 | 確認＋次週へ |

### 4.3 フェーズ進行原則

- 同一フェーズの確定処理は一度だけ実行する。
- 画面再読込後も確定済み操作を再実行しない。
- 必須操作が残っている場合のみ「次へ」を無効化する。
- イベントが存在しない週は該当フェーズを自動的に確認フェーズとして処理する。
- 軽微案件は週内に1〜3件生成し、ポン吉が自動処理する。

## 6. 財政システム

### 6.1 単位

市予算、収入、支出、借金、予備費の単位はすべて億円とする。小数は原則使わず整数で処理する。

### 6.2 常時表示

画面上部に次を固定表示する。

- 市予算
- 今週収支
- 翌週予測
- 衣装コイン

市予算と葉っぱコインは視覚的にも意味的にも分離する。

### 6.3 収入

- 市税
- 法人・経済活動税収
- 観光収入
- 施設収入
- 補助金
- 市債発行額

### 6.4 支出

- 行政基本費
- 継続政策費
- 施設維持費
- プロジェクト工事費
- 軽微案件処理費
- 調査費
- 災害・緊急対応費
- 市債利息

### 6.5 台帳

すべての資金変動は`ledgerEntries`へ記録する。

```js
{
  id: 'ledger-uuid',
  week: 3,
  phase: 'response',
  type: 'expense',
  category: 'disaster',
  label: '河川地区の緊急避難所開設',
  amount: -18,
  sourceId: 'event:flood-2026:response:evacuation',
  createdAt: '2026-07-28T00:00:00.000Z'
}
```

同じ`sourceId`を二重計上しない。

### 6.6 支出前表示

支出を伴う選択では必ず次を表示する。

- 初期費用
- 毎週維持費
- 現在予算
- 実施後残高
- 翌週予測
- 予備費への影響

費用は隠し情報にしない。

### 6.7 財政操作

- 予備費への積立・取り崩し
- 市債発行
- 継続政策の停止
- 大型事業の延期

市債には利息と選挙評価への悪影響を設定する。

### 6.8 財政危機とゲームオーバー

次のいずれかで財政危機状態に入る。

- 市予算が0億円未満
- 翌週予測が0億円未満
- 市債残高が300億円以上

財政危機中はポン吉が警告し、支出後の市予算がマイナス50億円未満になる新規大型事業を開始できない。

日曜決算時に市予算がマイナス150億円以下の場合、`financialCrisisWeeks`を1増やす。それ以外は0へ戻す。次のいずれかで財政破綻となる。

- 市予算がマイナス150億円以下の状態で2週連続決算
- 市債残高が500億円以上

## 7. 重点方針と委任

### 7.1 重点方針

毎週1つ選択する。

- 財政再建
- 子育て支援
- 観光振興
- 防災強化
- 工業誘致
- 環境都市
- デジタル化
- 暮らし優先

重点方針は税収、支出、イベント出現重み、議会、住民反応、ポン吉の自動処理へ影響する。

### 7.2 委任方針

ポン吉の軽微案件処理方針を設定できる。

- `balanced`: 費用と市民満足を均衡
- `saving`: 支出抑制を優先
- `citizen_first`: 市民満足を優先
- `focus_aligned`: 今週の重点方針を優先

自動処理結果は必ず土曜日または週次ダイジェストで報告する。

## 8. 大型プロジェクト

大型プロジェクトは複数週で進行する。

```text
proposal → investigation → council → construction → completed → operation
```

各プロジェクトに次を持たせる。

- 初期調査費
- 工事費総額
- 週ごとの支払額
- 維持費
- 期間
- 必要な議会支持
- 地区
- 期待効果
- 隠しリスク
- 中止時の損失

工事中の状態を街の見た目へ反映する。

## 9. 目標システム

### 9.1 週次目標

毎週2〜3件生成する。達成条件はその週の終了時に評価する。

例:

- 今週収支を黒字にする
- 防災力を55以上にする
- 特定住民の関係値を上げる
- 調査を実施して隠しリスクを確認する

### 9.2 任期目標

1任期を12週間とする。選挙時に評価する。

例:

- 市予算500億円以上
- 2地区をレベル3へ
- 支持率60以上
- 借金150億円未満

### 9.3 公約

新規ゲーム開始時に3候補から1つ選択する。

- 子育て都市
- 観光都市
- 災害に強い街

未達成時は選挙評価に大きな減点を与える。

## 10. 選挙

1任期は12週間とし、12週目の日曜決算後に選挙を実施する。

選挙評価は100点満点とし、次の比率で算出する。

| 評価項目 | 配点 |
|---|---:|
| 支持率 | 30点 |
| 公約達成 | 20点 |
| 住民関係値平均 | 15点 |
| 財政状態 | 15点 |
| 議会支持 | 10点 |
| 任期目標達成 | 10点 |

財政状態は市予算、予備費、市債残高を組み合わせて評価する。50点以上で再選、49点以下で落選とする。再選時は次の任期へ進み、落選時はゲームオーバーとする。

## 11. イベントパイプライン

イベントは4つのプレイ段階と1つの完了状態を持つ。

```text
preview → investigation → response → followup → resolved
```

### 11.1 予告

兆候と期限を提示する。ここでは結果を確定しない。

### 11.2 調査

調査費を支払うと、次の一部を開示する。

- 発生確率
- 被害規模
- 住民反応
- 利害関係者
- 選択肢ごとの追加費用

### 11.3 対処

確定費用は表示する。将来の副作用と完全な結果は表示しない。

### 11.4 続報

過去の投資、調査、対処、地区状態、住民関係から結果を決定する。結果適用後に`resolved`へ移行する。

イベントが段階を飛ばさないこと、同一結果を二重適用しないことを保証する。

## 12. 住民ストーリー

固定住民ごとに3〜5段階のストーリーを持たせる。

各ストーリー状態は次を含む。

- 現在章
- 発生条件
- 過去の選択
- 関係値
- 関係する地区
- 対立・協力キャラクター
- 終了状態

同一人物が短期間に連続登場しないクールダウンを設定する。住民ストーリーは週の重要案件または木曜フェーズで発生する。

## 13. 街の見た目

`cityVisualState`を政策・地区・事件状態から算出する。

主要要素:

- 商業の活気
- 歩行者数
- 観光客数
- 工場・トラック
- 緑地量
- 治安表現
- 雨、冠水、通行止め
- 工事中施設
- 空き店舗
- 市民感情の吹き出し

表示はSVGとCSSアニメーションを基本とし、Canvas、3D、WebGLは使用しない。

`prefers-reduced-motion`を尊重し、アニメーション削減設定では移動・揺れ・点滅を停止または短縮する。

## 17. エラーと二重処理防止

- フェーズ確定処理に一意な処理キーを付与する。
- 同じ台帳`sourceId`を二重計上しない。
- 同じプロジェクト工程を二度進行させない。
- イベント状態を逆戻りまたは飛び越しさせない。
- 週次決算中は操作をロックする。
- D1が利用できない場合は端末保存を継続する。
- D1へ保存失敗した場合はゲーム進行を止めず、同期状態を表示する。
- `0.7.0`以外の保存状態は不正扱いではなく「未対応旧状態」として無視する。
